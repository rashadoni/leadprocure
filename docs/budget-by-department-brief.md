## РОЛЬ И ЗАДАЧА

Ты работаешь в монорепозитории Leadprocure (NestJS + PostgreSQL 16 с RLS + React/Vite, pnpm workspaces).
Задача: реализовать **бюджетирование по отделам с периодами год/квартал/месяц** — полностью, все 7 этапов ниже, автономно, без остановок на уточнения.

**Первым делом прочитай `AGENTS.md` в корне** — там архитектурные правила (raw SQL через `RequestContextService`, RLS, деньги в minor units, аудит, чеклист нового модуля). Соблюдай их буквально: новый код должен быть неотличим от существующего.

## ЗАФИКСИРОВАННЫЕ РЕШЕНИЯ (не переспрашивать)

- Финансовый год = календарный. Период бюджета хранится датами (`period_start`/`period_end`), тип — `YEAR` / `QUARTER` / `MONTH`.
- Дата отнесения расхода = **дата одобрения заявки** (`approved_at`), а не `created_at`.
- Основная цифра — **обязательства**; факт (PO/инвойсы) идёт отдельной колонкой рядом.
- Заявка списывается ровно с **одного** бюджета, по специфичности: `отдел+категория` → `отдел` → `категория` → `общий (*)`.
- Одна валюта на бюджет. Пересчёт по курсу **не делаем**; вместо этого явное предупреждение в UI, что покупки в другой валюте в этот бюджет не попадают.
- Жёсткий блок одобрения при превышении — реализовать, но **выключенным по умолчанию** (`block_pct = null`). Порог предупреждения по умолчанию 80%.
- Перенос остатка (rollover) — через механизм ревизий бюджета, отдельной кнопкой, не автоматически.
- `department_id` на заявке — **nullable**: старые заявки не мигрируем, в отчётах они идут в бакет «Отдел не указан».
- Язык кода и комментариев — английский, как в существующем коде. UI-строки — во всех трёх локалях (az/ru/en).

## ЭТАПЫ

### Этап 1 — Справочник отделов + привязка заявки
Миграция `1720000000028-departments.ts`:
- `departments(id, buyer_org_id, code, name, parent_id, owner_user_id, is_active, created_at)`, `UNIQUE(buyer_org_id, code)`; RLS `buyer_org_id = app_org_id()` + `GRANT ... TO app_user` — по образцу миграции `…0023-categories`; `INSERT INTO release_versions`.
- `procurement_requests.department_id uuid REFERENCES departments(id) ON DELETE RESTRICT` (nullable) + индекс.
- `memberships.department_id uuid REFERENCES departments(id)` — для дефолта и видимости.

Код: новый `apps/api/src/modules/departments/departments.module.ts` по структуре `categories.module.ts` (GET — все buyer-роли, POST/PUT/DELETE — только `BUYER_ADMIN`, аудит `DEPARTMENT_CREATED/UPDATED/DELETED`, 409 на дубль кода, 409 при удалении используемого отдела); регистрация в `app.module.ts`; `departmentId` в DTO заявки + сохранение и выдача в `requests.module.ts`.

UI: селект отдела в форме заявки (`apps/web/src/pages/buyer/Requests.tsx`, рядом с категорией ~строка 114) с дефолтом из отдела пользователя, колонка и фильтр «Отдел» в таблице заявок, справочник отделов в настройках рядом со справочником категорий, ключи i18n в трёх локалях (`apps/web/src/i18n.tsx`).

**Готово, когда:** `apps/api/test/departments.e2e-spec.ts` покрывает CRUD, 409 на дубль, RLS-изоляцию двух buyer'ов, запрет удаления используемого отдела; заявка сохраняет и возвращает `departmentId`; весь e2e зелёный.

### Этап 2 — Периодичность (год/квартал/месяц) + дата обязательства
Миграция `1720000000029-budget-periods.ts`:
- `budgets`: `period_type text NOT NULL DEFAULT 'YEAR' CHECK (period_type IN ('YEAR','QUARTER','MONTH'))`, `period_start date`, `period_end date`; бэкфилл из `period_year` (01-01 … 12-31), затем `SET NOT NULL`; `CHECK (period_end >= period_start)`; уникальность `(buyer_org_id, name, period_year)` → `(buyer_org_id, name, period_start)`. Колонку `period_year` **оставить** (снос — отдельной миграцией позже).
- `procurement_requests.approved_at timestamptz`; бэкфилл `approved_at = updated_at WHERE status='APPROVED'` с комментарием в миграции, что это приближение.

Код: `approve()` проставляет `approved_at = now()`; `COMMITTED_SUBQUERY` переходит на `pr.approved_at BETWEEN b.period_start AND b.period_end`; DTO принимает `periodType` + `periodStart` (а также `year`+`quarter`/`month` как удобный вход, разворачиваемый на сервере); `GET /budgets` получает фильтры `?periodType=&from=&to=`.

UI: селект типа периода и выбор конкретного периода в форме; колонка «Период» вместо «Год»; фильтр периода над таблицей.

**Готово, когда:** e2e доказывает, что квартальный и месячный бюджеты считают только свой период, и что заявка, созданная 28 декабря и одобренная 5 января, попадает в **январский** период, а не в прошлогодний.

### Этап 3 — Бюджет по отделам + правило «один бюджет на заявку»
Миграция `1720000000030-budget-departments.ts`: `budgets.department_id uuid REFERENCES departments(id)` (NULL = все отделы) + индекс `(buyer_org_id, department_id, period_start)`; по возможности `EXCLUDE USING gist` на пересечение периодов в одном разрезе `(buyer_org_id, department_id, category, currency)`.

Код: переписать движок утилизации — вместо «каждый бюджет сам суммирует подходящие заявки» сделать `LATERAL`-выбор **единственного** бюджета для каждой APPROVED-заявки по специфичности (`отдел+категория` → `отдел` → `категория` → `*`), утилизация = группировка по `budget_id`. Добавить эндпоинт отчёта **«расходы вне бюджета»** (заявки, которым бюджет не нашёлся). Фильтр `?departmentId=`; в ответе — код и имя отдела. Видимость: `BUYER_USER` видит бюджеты только своего отдела (через `memberships.department_id`), `BUYER_ADMIN`/`BUYER_APPROVER` — все.

UI: колонка «Отдел», сводка по отделам сверху (план / обязательства / остаток / %), плитка на дашборде показывает, какой отдел превысил.

**Готово, когда:** e2e доказывает, что перекрывающиеся общий и отдельский бюджеты не удваивают расход; заявка без отдела попадает только в общий бюджет; отчёт «вне бюджета» ловит непокрытую заявку.

### Этап 4 — Факт (PO/инвойсы) и снятие обязательств
- Денормализовать `department_id` на `purchase_orders` и `invoices` (проставлять при создании из заявки) — по цепочке `request → event → contract → PO` не ходить, она рвётся на прямых закупках.
- Три метрики: **План** (`amount_minor`) / **Обязательства** (APPROVED-заявки без PO) / **Факт** (выпущенные PO, оплаченные инвойсы). Правило против двойного счёта: как только по заявке выпущен PO, обязательство заявки заменяется суммой PO.
- `ALTER TYPE request_status ADD VALUE 'CANCELLED'` + эндпоинт отмены одобренной заявки (`BUYER_ADMIN`, обязательная причина, аудит) — иначе резерв висит вечно.

**Готово, когда:** e2e проходит цепочку заявка → PO → инвойс и доказывает, что расход не задвоился, а отмена заявки освобождает обязательство.

### Этап 5 — Пороги, предупреждения, уведомления
- Настройки на организацию: `warn_pct` (дефолт 80), `block_pct` (дефолт NULL = выключено), `allow_override`.
- Предпроверка **до** одобрения: ответ содержит прогноз «эта заявка израсходует N% бюджета X», UI показывает его в диалоге одобрения.
- Жёсткий блок при `block_pct` с override для `BUYER_ADMIN` и обязательной записью в аудит.
- Уведомление ответственному за отдел через существующий `app_notify` (миграция `…0010`) + письмо при переходе порога.

**Готово, когда:** при `block_pct = NULL` поведение одобрения не изменилось (существующие тесты зелёные), а при заданном пороге одобрение блокируется и пропускается только через override с записью в аудит.

### Этап 6 — Корректировки бюджета с историей
- Таблица `budget_revisions(budget_id, amount_before, amount_after, reason, created_by, created_at)`.
- Сумма бюджета меняется только через ревизию; `PUT /budgets/:id` больше не перезаписывает `amount_minor` молча.
- UI: «История изменений» в карточке бюджета. Rollover = ревизия бюджета следующего периода со ссылкой на источник.

**Готово, когда:** изменение суммы создаёт запись ревизии, история отдаётся в API и видна в UI.

### Этап 7 — Отчётность и накопившиеся дефекты
- Экспорт CSV/XLSX по текущему фильтру.
- Поле валюты в форме бюджета (сейчас его нет, подпись жёстко «AZN», хотя API валюту принимает).
- Явное предупреждение в UI про непопадание чужой валюты в бюджет.
- Валидация `budgets.category` по справочнику `procurement_categories`.
- Копейки парсить из строки, не через `Number(x) * 100`.
- `getOne` перестаёт тянуть весь список ради одной строки.
- Обновить `apps/web/src/guides.ts` (онбординг) и `ROADMAP.md`.

**Готово, когда:** экспорт отдаёт файл по текущему фильтру, из UI создаётся не-AZN бюджет, суммы с копейками сохраняются без дрейфа.
