# Как на самом деле выложен прод и как выложить его в следующий раз

Это слой 3 из `docs/DELIVERY-ARCHITECTURE.md` — тот, который там описан одной
строкой «всё, что уже построено в этом репозитории для выкладки». Здесь написано,
что именно построено, что из этого прод не использует, и один путь на следующий
раз. Выкладки по этому документу ещё не было: он готовится к решению владельца,
а само решение — отдельное.

Дата проверки: 31 октября — 1 ноября 2026. Всё ниже прочитано с живой машины, не
выведено из документов. Ни один контейнер, образ, том и файл прода при этом не
менялся.

---

## Главное в пяти строках

1. У пользователей работает коммит **`400f861`** от 12 августа 2026 — это доказано
   побайтовым сличением исходников внутри образа, а не записью в метке.
2. Непримененных миграций — **12**. Переход именно с этого состояния уже проверяется
   в CI на каждом PR (baseline `budget_runtime` = ровно `400f861`), и проверка зелёная.
3. **Выкладка без файла лицензии сломает создание тендеров.** Сейчас лицензии нет, и
   на `400f861` это безобидно; на `main` это 403 на «создать закупку».
4. Проверки из `infra/DEPLOY.md` не «забыли» и релизный скрипт не «обошли»: **ни
   того, ни другого никогда не было в тех каталогах, из которых прод собран.** Они
   написаны в конце октября, а прод собран в августе.
5. Собирать здесь нельзя и не получится: `scripts/release/build-images.sh` сам
   отказывается работать вне GitHub Actions. Путь ниже собирает в Actions.

Чего в этом документе намеренно нет — числа «насколько прод отстал». `main` движется
по несколько раз в час: за время подготовки этого текста отставание `400f861` прошло
274 → 276 → 278. Любое записанное здесь число устареет к тому моменту, когда его
прочитают, поэтому мерить его надо на месте:

```bash
git fetch origin && git rev-list --count 400f861..origin/main
```

На 1 ноября 2026, 02:54 — **278**. Важен не счёт, а то, что `400f861` — строгий
предок `origin/main` (расхождения ветвей нет) и что набор непримененных миграций
меняется только с новой миграцией в `main`, а не с каждым коммитом.

**Это уже проверено CI, и именно с этой точки.** В
`scripts/acceptance/migration-baselines.json` есть baseline `budget_runtime` с
`sha = 400f8616eceb02c8b56993a41adafc99aba70474` — то есть ровно коммит прода — и
списком его 40 миграций с хешами. `scripts/acceptance/upgrade-branches.cjs`
(джоба `acceptance`, шаг «Upgrade both applied migration histories without rewriting
them») поднимает чистую базу до этого baseline, кладёт туда существующий план
бюджета и догоняет её до текущего `main`, после чего проверяет, что:

- ни одна запись в `migrations` не переписана;
- план бюджета цел (сумма, статус, границы периода);
- `period_year` снят, `upload_grants` создана;
- повторный прогон не делает ничего (идемпотентность);
- **хеши всех уже применённых миграций не изменились** — то есть никто не правил
  применённую миграцию задним числом.

Все 75 хешей из обоих baseline сверены локально 31.10.2026 — расхождений нет, то
есть гейт сегодня проходит по настоящему состоянию прода, а не по устаревшему
слепку.

Чего этот гейт не покрывает: он работает на **синтетических** данных. Два UNIQUE из
таблицы выше падают не от схемы, а от истории. Поэтому они остаются вопросом
preflight, а не CI.

Порядок применения. У семи пар миграций в `main` совпадают метки времени
(`0028`–`0034` существуют дважды: ветка аудита и ветка бюджетов). На проде уже стоят
`0035`–`0039`, поэтому непримененные `0028`–`0034` пойдут **после** них — TypeORM
гонит непримененные по возрастанию метки и на порядок применения в прошлом не
смотрит. Что это безопасно, показывает тот же `upgrade-branches.cjs`: baseline
`budget_runtime` именно так и устроен. Отдельно проверять это руками не нужно, но
знать стоит: «номер меньше» здесь не значит «применится раньше».

Миграции необратимы. `0043` на `down()` бросает ошибку явным текстом
(«Forward-only membership key correction»), и так же устроены остальные начиная с
`0028`. **Откат образа api не откатывает схему.** Единственный откат схемы —
восстановление из резервной копии.

### Что сломается без лицензии — главный риск этой выкладки

Прод работает в `NODE_ENV=production`, и лицензии у него нет: в контейнере api
**нет** ни `LICENSE_FILE`, ни `LICENSE_PUBLIC_KEY_B64`, список монтирований пуст
(`Mounts: []`), каталога `infra/license/` в воркитри прода не существует, в
`.env.prod` нет ни `LICENSE_PUBLIC_KEY_B64`, ни `LICENSE_DIR`.

На `400f861` это ничего не ломает: без лицензии `EntitlementService` уходит в
dev-fallback и выдаёт `enterprise/valid` — это и видно в живом `/health`.

На `main` поведение другое и сделано намеренно:

```
this.source = this.cfg.nodeEnv === 'production' ? 'missing' : 'development';
this.snap   = this.source === 'missing' ? this.restricted() : this.devFallback();
```

`restricted()` даёт `status: 'expired_restricted'`, а `assertCanCreateNew()` на таком
статусе бросает 403. Вызывают его `sourcing.service.ts:86` и `:136` (создание и
публикация закупки), `auction.service.ts:36` (старт аукциона) и `feature.guard.ts:22`.
Набор функций при этом остаётся enterprise, то есть разделы не исчезнут — перестанет
работать **создание нового**: объявить закупку, опубликовать её, запустить аукцион.
Живые тендеры не прерываются, это предусмотрено.

CI этого не поймает и не должен: `fresh-install.sh` как раз проверяет, что без
лицензии прод ограничен, и отдельно — что подписанный файл лицензии снимает
ограничение. Гейт работает правильно; просто у прода сейчас нет того, что он
требует. Поэтому лицензия — не пункт чеклиста, а **условие, без которого выкладку
начинать нельзя**.

## 2. Почему прод не проходит через проверки репозитория

Не потому, что их обошли или забыли. Проверки и релизный скрипт написаны позже
сборки прода и никогда не лежали в тех каталогах, из которых он собран.

**Оснастки никогда не было там, где собирается прод.** Это главное и самое простое
объяснение, и оно точнее, чем «проверки обошли». Проверить можно в одну строку:

```bash
git ls-tree -r --name-only 400f861 -- scripts/release/   # пусто
```

| Где | Коммит | Дата | `scripts/release/build-images.sh` | «absence of demo credentials» в `DEPLOY.md` |
|---|---|---|---|---|
| воркитри, из которого собраны api/web/postgres | `400f861` | 12.08.2026 | нет | нет |
| канонический чекаут `/home/rashad/projects/Leadprocure` (minio, clamav, ai) | `2a94cc5` | **13.07.2026** | нет | нет |

`scripts/release/` появился в `main` 28 октября 2026 (`c2a746e`), строка про
«absence of demo credentials» — 27 октября (`abc3540`). Образ api собран 12 августа.
То есть в тот момент ни скрипта, ни этого списка проверок **не существовало вообще**:
никто ничего не обходил и не забывал. Релизная дисциплина написана через два с
половиной месяца после сборки и с тех пор не применялась ни к чему — потому что
выкладки с тех пор не было.

Отдельно стоит заметить про канонический чекаут: он на `main`, но этот `main` от
**13 июля** и на 321 коммит позади `origin/main`. То есть ни один из двух каталогов,
из которых поднят прод, не годится как источник релиза — в обоих нет ни релизного
скрипта, ни нынешнего compose-файла. Оснастка живёт только в свежих воркитри,
отрезанных от текущего `main`.

**Шапка compose предлагает ровно тот путь, которым прод и собран.**
`infra/docker-compose.prod.yml`, строка 3: `docker compose -f docker-compose.prod.yml
--env-file .env.prod up -d --build`. Эта строка противоречит и
`scripts/release/README.md` («do not run `up --build` on Contabo»), и
`~/.claude/CLAUDE.md` (тяжёлые docker-сборки на Contabo запрещены) — но в августе ни
того, ни другого текста ещё не было, а строка была и осталась. Пока она там, её и
будут запускать.

**Следствие первое — нет меток.** `revision` и `source` ставит только
`build-images.sh`. Без них про образ нельзя сказать, какой в нём коммит: восстановить
его удалось сличением 93 файлов, и это работает лишь потому, что api тащит исходники
в образ. Для web, где в образ попадает только минифицированный бандл, такой приём уже
не сработал бы — и это тот случай, который ждёт следующую сессию, если выложить без
метки ещё раз.

**Следствие второе — нет и проверок.** Всё, что перечислено в `infra/DEPLOY.md:104`
(«verify health **and license source/status**, role/organization isolation,
procurement approval and sealed-bid visibility, document access/AV, HTTPS refresh
cookies/CORS and absence of demo credentials. Record deployed SHA…»), — пост-деплойные
шаги **релизного** пути; `up -d --build` заканчивается на «контейнер поднялся».
Про подсказку с паролем точная формулировка такая: утёкший web-образ собран
12 августа, проверка «absence of demo credentials», которая её поймала бы, написана
27 октября, а нашли подсказку 31-го — глазами, не проверкой. И «Record deployed SHA»
никто не записывал, поэтому коммит и пришлось восстанавливать хешами файлов.

**Релизный скрипт здесь запустить нельзя.** `build-images.sh`, строка 5:

```bash
test "${GITHUB_ACTIONS:-}" = true || { echo 'Use the hosted release-artifacts workflow' >&2; exit 1; }
```

Он отказывается работать вне GitHub Actions, требует чистого чекаута
(`git status --porcelain` должен быть пуст) и полный 40-символьный SHA. То есть выбор
«собирать здесь или в Actions» уже сделан в репозитории, и сделан в пользу Actions.
Запрет из `~/.claude/CLAUDE.md` и этот `test` говорят одно и то же.

**Чего в репозитории действительно нет.** `infra/docker-compose.prod.yml` описывает
api и web только через `build:` — у них нет `image:`, поэтому готовый образ из
релизного архива compose подставить некуда. У `minio` этот приём уже применён
(`image: leadprocure-object-storage:source-7aac2a2` + `pull_policy: build`), до api и
web его просто не довели. Это и есть то место, где релизный путь обрывается: архив
собирается, проверяется, скачивается — и дальше его нечем подключить, кроме ручного
переименования образов. Поэтому к этому документу приложен
`infra/docker-compose.release.yml`.

**Слой 3 в `docs/DELIVERY-ARCHITECTURE.md`** описан одной строкой и ни на что не
ссылается. Слои 1, 2 и 4 там конкретны до команд; слой 3 — нет, и прод живёт ровно в
этом пробеле.

## 3. Путь на следующий раз

Один путь. Сборка — в GitHub Actions (здесь её запретили и `CLAUDE.md`, и сам
скрипт). На Contabo остаются только загрузка готового образа, запуск и проверки.

Выкладываются **только api и web**. Postgres, MinIO, ClamAV и ai-orchestrator не
трогаются: `main` меняет образ MinIO на собираемый из исходников, а
`infra/DEPLOY.md` прямо запрещает подменять образ MinIO над существующим томом
(«Existing MinIO volumes are not proven upgrade-compatible by a fresh-volume test.
Never replace their image or delete data as a workaround»). Замена хранилища — своя
задача со своей приёмкой на настоящем томе.

### Условия, без которых не начинать

- [ ] `acceptance` и `fresh-install` зелёные на том самом коммите `main`, который
      выкладывается (не на PR, а на `main` — `workflow_dispatch` на нём).
- [ ] **Лицензия готова** (см. §1): каталог оператора с `leadprocure.license`,
      `LICENSE_DIR` на него и `LICENSE_PUBLIC_KEY_B64` в `.env.prod`. Без этого
      после выкладки перестанет создаваться новая закупка. Приватный ключ эмитента
      на хост не попадает.
- [ ] **Резервная копия базы снята и восстановление проверено отдельно.** Миграции
      необратимы; откат образа схему не вернёт. На 28.10.2026 резервной копии
      Leadprocure на хосте не нашли. `scripts/acceptance/backup-restore.sh`
      использовать нельзя — он намеренно заперт на изолированный CI.
- [ ] Preflight пройден и дубли согласованы (ниже).
- [ ] Владелец сказал «давай» на короткий список из слоя 4.

### Шаг 1. Preflight (только чтение, с прода)

```bash
docker exec -i leadprocure-prod-postgres-1 psql -U leadprocure_owner -d leadprocure -f - < scripts/acceptance/preflight-readonly.sql
```

Весь файл обёрнут в `BEGIN READ ONLY` … `ROLLBACK` и ничего не меняет. Выкладку
блокируют ненулевые `duplicate_invoice_lines`, `duplicate_evaluation_scores` и
`duplicate_memberships` — на них упадут `0029` и `0043`. Разбирать такие строки
руками, по одной, не удаляя финансовых документов: какая из двух ролей или строк
счёта должна остаться, не может решить ни скрипт, ни агент. `0043` при падении сам
называет конкретные пары пользователь/организация.

`installed_licenses` ожидается `0`, и это и есть причина требовать файл лицензии до
выкладки. `legacy_invoice_lines_requiring_tax_review` — исторические строки счетов
без снимка НДС; на 28.10.2026 их было пять. Миграция их не пересчитывает и не
удаляет, налоговая политика по ним — отдельное решение.

### Шаг 2. Собрать образ в Actions

Запустить `release-artifacts.yml` на `main` через `workflow_dispatch` с
`public_api_url = http://75.119.156.234:3100` (текущий адрес; менять его — отдельное
решение, он вшивается в бандл и подписывает presigned-ссылки).

Workflow соберёт api и web с метками `org.opencontainers.image.revision` (полный SHA)
и `org.opencontainers.image.source`, с `VITE_DEMO_HINT` пустым **из скрипта**, а не
из env, выгрузит `leadprocure-images.tar.gz` + `manifest.json`, затем на том же
воркере удалит теги, загрузит архив заново и сверит восстановленные образы. Артефакт
`leadprocure-release-<SHA>` живёт 7 дней.

Ожидаемый SHA брать из прогона в GitHub, **не** из скачанного `manifest.json`.

### Шаг 3. Проверить пакет на хосте

### Шаг 4. Пометить то, что работает сейчас (точка отката)

### Шаг 5. Загрузить образы


### Шаг 6. Выложить api и web

**Compose-файлы берутся из чекаута выложенного SHA, а не из тех каталогов, где
сейчас живёт прод.** Это не придирка: в каноническом `infra/docker-compose.prod.yml`
(`2a94cc5`, 13 июля) нет ни монтирования лицензии, ни зависимости от
`createbuckets`, ни тем более `docker-compose.release.yml` (§2). Запуск оттуда поднял
бы api без лицензии и молча — ровно та поломка, которую весь этот документ пытается
не допустить. Поэтому: отрезать воркитри на выложенном SHA и работать из него.
`.env.prod` при этом остаётся живой — тот, что лежит в
`…/budget-by-department-audit-4e2173/infra`; ветку и файлы этого воркитри не трогать,
из него читается только env.

```bash
REL=/путь/к/воркитри/на/выложенном/SHA       # git worktree add … ПОЛНЫЙ_SHA_40
ENVP=/home/rashad/projects/Leadprocure/.claude/worktrees/budget-by-department-audit-4e2173/infra/.env.prod

RELEASE_SHA=ПОЛНЫЙ_SHA_40 LICENSE_DIR=/абсолютный/путь/к/каталогу/лицензии \
docker compose -p leadprocure-prod \
  --project-directory "$REL/infra" \
  -f "$REL/infra/docker-compose.prod.yml" \
  -f "$REL/infra/docker-compose.release.yml" \
  --env-file "$ENVP" up -d --no-build --no-deps api web
```

`-p leadprocure-prod` обязателен — иначе compose создаст новый проект вместо того,
чтобы заменить работающие контейнеры. `--project-directory` задаёт каталог, от
которого считаются относительные пути в compose-файле; `LICENSE_DIR` абсолютным
путём выводит каталог лицензии из-под него (проверено `docker compose config`:
монтирование разрешается в указанный абсолютный путь, `read_only: true`,
`create_host_path: false`).

`infra/docker-compose.release.yml` добавлен этим документом: он подставляет api и web
готовые образы `leadprocure-api:${RELEASE_SHA}` / `leadprocure-web:${RELEASE_SHA}` с
`pull_policy: never`, чтобы compose не попытался ни собрать их, ни скачать.
`--no-build` и `--no-deps` обязательны: без `--no-deps` compose потянет
`postgres`/`createbuckets` и захочет подменить образ MinIO.

Миграции пойдут сами: `apps/api/docker-entrypoint.sh` на каждом старте выполняет
`pnpm --filter api migration:run`. Все 12 идут **одной транзакцией** (у TypeORM CLI
это поведение по умолчанию), поэтому падение любой откатывает все — именно это
утверждает `scripts/acceptance/upgrade-check.cjs`, проверяя, что после сбоя
`upload_grants` не остаётся. Если контейнер api не поднялся — смотреть
`docker logs leadprocure-prod-api-1`: первые строки покажут, какая миграция упала и
на каких данных.

### Шаг 7. Проверить (это и есть `infra/DEPLOY.md:104`)

```bash
curl -fsS http://75.119.156.234:3100/health
```

Ждать `status: ok` и **`licenseSource: installed` или `file`** со
`licenseStatus: valid`. `licenseSource: missing` означает, что лицензия не доехала и
создание закупок уже отвечает 403 — откатываться по шагу 8. Если поля
`licenseSource` в ответе нет вовсе, запустился старый образ: на `400f861` его ещё не
было.

```bash
docker run --rm --entrypoint sh leadprocure-web:ПОЛНЫЙ_SHA_40 -c \
  'for p in acme.test supply-one.test demo1234 Demo123 VITE_DEMO_HINT; do echo "$p -> $(grep -rlF "$p" /usr/share/nginx/html 2>/dev/null | wc -l)"; done'
```

Все шесть должны быть `0` — это проверка «absence of demo credentials», которой на
нынешнем пути нет. Её можно и нужно выполнить **до** шага 6, на загруженном образе.

Дальше — руками в браузере, по `infra/DEPLOY.md:104`: вход/обновление сессии/выход,
изоляция организаций и ролей, согласование заявки, невидимость сумм в закрытых
предложениях до вскрытия, загрузка и скачивание документа с антивирусом, presigned-
загрузка из браузера на `:9002`. Демо-сид и сброс базы на проде не запускать никогда.

### Шаг 8. Откат

Те же файлы и тот же каталог, что в шаге 6 (`$REL`, `$ENVP`) — меняется только тег:

```bash
docker image tag leadprocure-prod-api:rollback-400f861 leadprocure-api:rollback
docker image tag leadprocure-prod-web:rollback-400f861 leadprocure-web:rollback
RELEASE_SHA=rollback LICENSE_DIR=/абсолютный/путь/к/каталогу/лицензии \
docker compose -p leadprocure-prod \
  --project-directory "$REL/infra" \
  -f "$REL/infra/docker-compose.prod.yml" \
  -f "$REL/infra/docker-compose.release.yml" \
  --env-file "$ENVP" up -d --no-build --no-deps api web
```

Воркитри `$REL` держать до конца выкладки: без него откатываться будет нечем, кроме
каталогов, которые для этого не годятся (§2).

**Это откат приложения, а не схемы.** Миграции необратимы, `0043` на `down()` бросает
ошибку намеренно. Старый api на новой схеме — непроверенное состояние: он годится,
чтобы вернуть пользователям работающий экран на время разбора, но не как конечная
точка. Если схему нужно вернуть — только восстановление базы из копии, снятой на
шаге «условия», и тогда api и web обязаны вернуться на `400f861` вместе с ней.

### Шаг 9. Записать

В журнал сессии: выложенный полный SHA, ID обоих образов, ID и место резервной
копии, вывод preflight, точку отката (`rollback-400f861` + оба `sha256`), результаты
проверок шага 7 и что из них не выполнялось. Без этой записи следующая сессия снова
будет восстанавливать коммит по хешам файлов.

## Что остаётся незакрытым

- **Резервной копии прода нет.** Это условие, а не замечание: без проверенного
  восстановления необратимые миграции выкладывать некуда.
- **Лицензии нет**, и на `main` это ломает создание закупок (§1). Чей файл лицензии
  ставить — своя лицензия оператора или клиентская — решает владелец.
- Публичного HTTPS нет, маршрут остаётся HTTP на IP; `REFRESH_COOKIE_SECURE=false`
  держится под него. Проверка cookie/CORS через настоящий TLS — NOT RUN.
- Смешанные каталоги Compose (§1) этим путём не чинятся, а обходятся через `-p` и
  `--no-deps`. Привести проект к одному каталогу — отдельная задача, и она
  пересоздаёт контейнеры.
- **Канонический чекаут `/home/rashad/projects/Leadprocure` стоит на `main` от 13 июля**
  (321 коммит позади) и релизной оснастки в нём нет. Поэтому в шаге 6 compose-файлы
  берутся из отдельного воркитри на выложенном SHA. Подтянуть канонический чекаут —
  отдельное решение: из его `infra/` подняты работающие minio/clamav/ai-orchestrator,
  и `docker compose` оттуда после обновления файла захочет их пересоздать.
- Шапка `infra/docker-compose.prod.yml` всё ещё предлагает `up -d --build` — ту самую
  команду, которой прод и собрали. Пока она там, её будут запускать.
- Замена MinIO на собираемый из исходников образ и обновление ClamAV на `stable` в
  этот путь не входят.
