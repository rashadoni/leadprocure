# Что проверки этого репозитория на самом деле ловят — аудит, 10.11.2026

Повод: 10 ноября 2026 в продукте нашлись четыре настоящих дефекта, и ни один не нашли
тесты. Все четыре нашлись при записи обучающих видео — когда озвучка сказала про экран то,
чего на нём не было. Гейт при этом был зелёным: **между 1 и 10 ноября прогон приёмки
завершился успехом 337 раз**, и во всех этих прогонах три из четырёх дефектов лежали в
продукте (`gh run list --workflow acceptance.yml`, 400 последних прогонов).

Код продукта в этом заходе не менялся — это аудит. Все четыре дефекта уже починены
(PR #175, #177, #178); здесь разбирается не они, а почему их не увидели 488 проверок api и
55 браузерных.

Коротко, одной фразой: **оба набора сильны в том, что меряют, а дефекты жили в промежутке
между ними.** На стороне api — 9 969 строк проверок на 15 052 строки кода, почти без слабых
утверждений (на 449 тестов ровно один проверяет только код ответа). На стороне экрана —
3 305 строк, из которых большая часть про раскладку, подсказки и ширину телефона, а весь
глубокий путь через интерфейс — **один** тест. Шов «экран → запрос → экран» не меряет
никто, и три дефекта из четырёх лежали ровно на нём.

## Дыры по убыванию цены

Порядок — по тому, во что обойдётся срабатывание, а не по порядку обхода файлов.

### 1. Деньги на первом экране обеих ролей не проверяет ничто

`GET /dashboard/buyer` и `GET /dashboard/supplier` — 317 строк
([dashboard.module.ts](apps/api/src/modules/dashboard/dashboard.module.ts)) с извлечением
суммы без НДС (`poNet`, `lineNet`), экономией по тендерам и очередью задач — **не имеют ни
одного теста api**. В наборе api строка `dashboard` встречается только у
`/dashboard/spend-analytics`. Браузерная проверка этого экрана целиком такая:

```ts
test('dashboard shows real KPI money', async () => {        // smoke.spec.ts:356
  await visit(page, '/buyer/dashboard');
  await expect(page.locator('text=AZN').first()).toBeVisible({ timeout: 10_000 });
});
```

Название обещает «настоящие деньги KPI», утверждение проверяет, что где-то на странице
встречаются три буквы AZN. Второе упоминание `/dashboard/buyer` в наборе — тест про
упавшую загрузку ([smoke.spec.ts:533](apps/web/tests/smoke.spec.ts:533)), и он подменяет
ответ своим, то есть настоящих чисел тоже не видит.

Цена: неверная сумма на экране, который видит каждый покупатель при входе и который
показывают на демонстрациях. Арифметика НДС здесь своя, не переиспользованная.

Дешевле всего: один тест api на `/dashboard/buyer` поверх уже готовой фикстуры
`order-card.e2e-spec.ts` — присудить, выписать заказ, принять, и сверить `awardedSpend` и
`savings` с суммами, которые тест сам задал. Один тест, одна фикстура, никакого
браузера.

### 2. Отказ в заявке не проверяет ничто

`POST /requests/:id/reject`
([requests.module.ts:273](apps/api/src/modules/requests/requests.module.ts:273)) — 25 строк
с проверкой роли шага, отдельным правилом для `BUYER_FINANCE`, отметкой шага цепочки,
переводом заявки в `REJECTED` и записью в аудит. В обоих наборах нет ни одного обращения к
этому адресу: `grep -rn "/reject" apps/api/test apps/web/tests` находит только
`/invoices/:id/reject` и `/budgets/:id/reject`. Строка `REQUEST_REJECTED` не встречается в
тестах нигде.

То есть «нет» — вторая половина решения, ради которой вся цепочка согласования и
существует, — не проверена ни разу. Сломанный отказ выглядит как заявка, застрявшая в
`SUBMITTED` с зарезервированными деньгами, или как отказ не на том шаге.

Дешевле всего: три строки в [approval.e2e-spec.ts](apps/api/test/approval.e2e-spec.ts) —
отказать на первом шаге трёхшаговой цепочки и проверить `status`, `rejected_by`, отметку
шага и то, что резерв бюджета снялся.

### 3. Дефект, уехавший на прод 10 ноября, до сих пор не закрыт сторожем

Дефект №3 из списка (строка отдела читалась как «без владельца», пока `/settings/users` в
полёте, и навсегда, если тот запрос упал) починен в #178 заменой условия:

```
было:  d.owner_user_id && ownerStatus(d) !== 'ACTIVE'
стало: d.owner_user_id && !activeUsers.some(u => u.id === d.owner_user_id)
```

**Проверено опытом** (перебор состояний,
`scratchpad/exp-cond.mjs`): из 12 возможных состояний экрана два условия расходятся ровно
в **одном** — когда `users` пуст, то есть пока `/settings/users` не сел или если он упал. Ни
один тест этого состояния не создаёт: `grep -rn "settings/users" apps/web/tests` даёт только
обращения-фикстуры, `page.route` на этот адрес нет нигде (а на другие адреса он есть в 16
местах). Верните старое условие сегодня — гейт останется зелёным.

Цена: повторение того же дефекта, который уже один раз уехал к пользователям, и повторение
молча.

Дешевле всего: четыре строки в уже существующем файле
[department-owner-reachable.spec.ts](apps/web/tests/department-owner-reachable.spec.ts) —
`page.route('**/settings/users', r => r.fulfill({ status: 500, body: '{}' }))`, затем то же
утверждение `toHaveValue(leaver.id)`, что и без подмены. Фикстура уже готова.

### 4. Сорок путей записи с экрана не нажимает ни один браузерный тест

В интерфейсе 87 вызовов записи на 75 различных адресов (`api.post/put/patch/del` в
`apps/web/src`). **40 из этих адресов не упоминаются ни в одном браузерном тесте** — ни кликом, ни
ожиданием ответа. Это ровно класс дефекта №1 («поле на экране есть, в запрос не попало»), и
он ждёт в сорока местах. Самые дорогие:

| Путь записи | Экран | Что проверяет api |
|---|---|---|
| `/suppliers/:id/scorecard` (и, только как фикстура api, `/suppliers/:id/invite`, `/suppliers/relationships/:id/status`) | Реестр поставщиков (`dir-invite`, `sup-approve`, `sup-block`, `sup-score` — семь зацепок, ни одной читаемой тестом) | да, `suppliers.e2e`, `audit-regressions` |
| `/catalogs/:id/order`, `/catalogs/:id/activate`, `/catalogs/from-contract/:id` | Каталоги — заказ из каталога создаёт настоящий заказ | да, `catalogs.e2e` |
| `/orders/:id/amendments`, `/orders/:id/amendments/:id/decision` | Изменение заказа: меняет сумму заказа | да, `amendments.e2e` |
| `/budgets/:id/phasing`, `/budgets/:id/rollover`, `/budgets/import` | Бюджеты: разбивка плана по месяцам, перенос остатка | да, `budgets.e2e` |
| `/logistics/po/:id/shipment`, `/logistics/po/:id/events` | Логистика целиком | да, `logistics.e2e` |
| `/verification/cases/:id/decide`, `/verification/presign` | Проверка поставщика | да, `verification.e2e` |
| `/events/:id/qna`, `/events/:id/addenda`, `/events/:id/waive-standstill`, `/events/:id/cancel-award`, `/events/:id/withdraw` | Карточка тендера и карточка поставщика | да |
| `/notifications/read-all`, `/notifications/:id/read` | Лента уведомлений | **нет, нигде** |

Отдельно: `GET /suppliers/directory` и `GET /documents/bid-doc/:id/download` не упоминаются
ни в одном тесте ни одного набора.

Цена: тихая потеря действия. Приёмник работает, экран показывает кнопку, запрос уходит без
поля — и это ровно то, что уже случилось с владельцем отдела.

Дешевле всего не закрывать сорок мест по одному, а завести **одну проверку формы** там, где
запись создаёт деньги: заказ из каталога и решение по изменению заказа. По одному круговому
тесту на каждую (заполнить форму → прочитать строку назад → сверить с тем, что вводили).

### 5. Стенд браузерного набора пишется только сырым SQL — поэтому проверки «на экране есть X» ничего не говорят о продукте

[seed.ts](apps/api/src/seed.ts) — 183 строки, 13 `INSERT INTO` напрямую в таблицы, **ни
одного обращения к api**. Отделы вместе с владельцами создаются так:

```sql
INSERT INTO departments(buyer_org_id, code, name, owner_user_id) VALUES ($1,$2,$3,$4)
```

Поэтому проверка, добавленная в #174 именно для того, чтобы экран договаривал за озвучку:

```ts
expect(ownerValues.filter(Boolean).length,            // smoke.spec.ts:694
  'not one department names an owner').toBeGreaterThan(0);
```

— зеленела при форме, которая владельца не отправляла: хоть один отдел с владельцем на
стенде есть всегда, его написал seed. Утверждение «на экране есть владелец» на этом стенде
не может отличить работающую форму от неработающей.

Цена: это механизм, по которому прошёл дефект №1 — мимо теста, написанного специально под
него.

Дешевле всего: правило, а не код. Проверка состояния, которое создал seed, не доказывает,
что продукт умеет это состояние создавать. Там, где важна запись, тест обязан записать сам
— через интерфейс (как теперь `smoke.spec.ts:589`) или хотя бы через api.

### 6. Весь глубокий путь через интерфейс — один тест, и прогон останавливается на первом падении

[evaluation.spec.ts](apps/web/tests/evaluation.spec.ts) — **один** `test()` (71 утверждение
в самом файле плюс шесть подключённых файлов-помощников, ещё 194), который через экран
проводит: подача закрытой ставки (RFI/RFP, три языка) →
вскрытие → оценка → присуждение → договор → заказ → выпуск/подтверждение → приёмка товара →
счёт → утверждение → оплата, плюс панель аукциона и его закрытие, плюс гонки и отказы на
счетах. Это настоящая глубина — и она вся в одном `test()`.

Запускается набор с `--workers=1 --max-failures=1`
([acceptance.yml](.github/workflows/acceptance.yml)), файлы идут по алфавиту: `analytics`,
`budget-approval`, `department-owner-reachable`, `evaluation`, … Падение в первом файле
означает, что весь путь закупки в этом прогоне не проверялся вовсе, а красный прогон не
говорит ничего об остальном.

Цена: при любом падении раньше `evaluation` гейт перестаёт быть гейтом и становится
«что-то сломалось» — а понять по отчёту, что именно осталось непроверенным, нельзя: в нём
будет одно упавшее имя теста на весь путь закупки.

Дешевле всего: разнять этот тест по этапам (`test.describe.serial` с общей фикстурой) —
падение на вскрытии перестанет скрывать счета, и отчёт назовёт этап.

### 7. Автоповтор утверждений Playwright слеп к состоянию «пока второй запрос не сел»

`expect(...)` в Playwright повторяется до таймаута. Это значит, что **любой экран, который
становится правильным со временем, зелен по построению** — а дефект №3 был именно таким:
`/departments` садится раньше `/settings/users`, и в этом окне строка читалась неверно.
Обычным утверждением такое не поймать никогда; нужна задержка или отказ запроса вручную
(`page.route`), и репозиторий это умеет — 16 мест, из них ни одного на паре
«отделы + пользователи».

Цена: класс дефектов «правильно, но не сразу» невидим целиком. Сюда же попадает всё, где
экран собирается из двух запросов.

Дешевле всего: там, где экран читает два источника, один из них должен быть задержан или
уронен в тесте. Шаблон уже есть в
[helpers/invoice-detail-race.ts](apps/web/tests/helpers/invoice-detail-race.ts).

### 8. Почта наблюдаема в одном файле и только для безадресной рассылки

Провайдер почты подменяется только в двух файлах api
([mail.e2e-spec.ts](apps/api/test/mail.e2e-spec.ts) и добавленном в #177
[notify-recipient.e2e-spec.ts](apps/api/test/notify-recipient.e2e-spec.ts)). Во всех
остальных 43 файлах работает `ConsoleMailProvider`: письмо «уходит» в лог, и не смотрит на
него никто. До #177 все 4 теста `mail.e2e-spec.ts` проверяли только безадресную рассылку
(`notifyOrg`), а адресной ветки (`userId`) не касался никто — это и есть дефект №2.

Цена: канал, который выключается молча. Теперь закрыт для бюджетного предупреждения, но
подмена провайдера по-прежнему живёт в двух файлах из 45, и любое новое адресное письмо
окажется ровно в том же положении.

Дешевле всего: подменять провайдера в общей фикстуре (`helpers.ts`), чтобы любое письмо
любого теста попадало в наблюдаемый список. Тогда «ушло в никуда» становится видно без
отдельного файла.

### 9. Одна из двух обязательных проверок смотрит на интерфейс через наличие `<script src=`

`fresh-install` — вторая обязательная джоба. Её проверка веб-части целиком:

```js
assert.equal(web.status, 200);                                  // fresh-install-check.cjs:95
assert.match(await web.text(), /<script[^>]+src=/);
```

Остальное в ней — про установку (режим лицензии, S3-подписи, ClamAV, права на скачивание) и
один бюджетный путь, и это ценно. Но считать её проверкой интерфейса нельзя: она
подтверждает, что `index.html` отдаётся и содержит тег скрипта.

Цена: чувство, что интерфейс проверяют два гейта, тогда как его проверяет один.

### 10. Прочитанность уведомлений и лента уведомлений не проверяет ничто

`POST /notifications/read-all` и `POST /notifications/:id/read` не упоминаются ни в одном
тесте; строка `notification` в браузерном наборе встречается один раз, и то в комментарии
([smoke.spec.ts:439](apps/web/tests/smoke.spec.ts:439)). Сами уведомления при этом
проверяются много где — но только как строка в базе, никогда как лента, которую человек
читает и гасит.

Цена: уведомления, которые нельзя погасить, или кнопка «прочитать всё», гасящая чужие.
`UPDATE notifications SET read_at = now() WHERE read_at IS NULL` опирается на RLS целиком.

### 11. Проверки, которые пересчитывают формулу продукта его же числами

```ts
it('the rollup forecasts where the period ends up at the current rate', async () => {
  const row = rows.find((r: any) => r.usedMinor > 0);        // budgets.e2e-spec.ts:244–251
  expect(row.forecastMinor).toBe(Math.round((row.usedMinor / row.elapsedPct) * 100));
```

Ожидаемое значение выводится из тех же `usedMinor` и `elapsedPct`, которые вернул сервер.
Если `elapsedPct` считается не так, как надо (а это ровно то, ради чего делали разбивку по
месяцам), проверка согласится с любым ответом. Того же рода — `remainingMinor` =
`amountMinor − committedMinor` ([budgets.e2e-spec.ts:115](apps/api/test/budgets.e2e-spec.ts:115),
`:601`, `:614`, `:756`): это проверки внутренней согласованности, полезные, но они пройдут
и тогда, когда оба числа неверны одинаково.

Цена: небольшая, но считать такие строки покрытием арифметики нельзя. В том же файле есть
и правильный образец — [budgets.e2e-spec.ts:239](apps/api/test/budgets.e2e-spec.ts:239),
где список сверяется с суммой, которую тест задал сам.

## 1. Почему четыре дефекта прошли мимо

### Дефект 1 — форма создания отдела не отправляла `ownerUserId`

**Что было.** Форма собирала код, название и родителя; приёмник `POST /departments` всегда
принимал `ownerUserId` ([dto](apps/api/src/modules/departments/departments.module.ts:22)).
Любой отдел, созданный в продукте, рождался без владельца — то есть бюджетное
предупреждение по нему уходило всей организации, пока озвучка говорила «у каждого отдела
есть владелец». Жил с 28.10.2026 (`1fa3075`) до 10.11.2026 (`1da7458`).

**Какой тест должен был поймать.** Браузерный: создать отдел формой и прочитать владельца
назад. Такого теста не было. Ближайший — «creating a draft request works through the UI,
including its department» (до правки `smoke.spec.ts:557`):

```ts
const depForm = page.locator('.card', { hasText: /Отделы|Departments|Şöbələr/ }).locator('form');
await depForm.locator('input').first().fill(code);
await depForm.locator('button.btn').click();
await expect(dep).toBeVisible({ timeout: 10_000 });
```

Три беды в пяти строках. Утверждение — «в таблице появилась ячейка с кодом», то есть
**наличие элемента вместо значения**: про владельца оно не говорит ничего и не может. Поля
адресуются **по месту** (`input` первый) — ровно против чего предупреждает комментарий в
начале этого же теста («a selector that silently stops matching is worse than no test»); код случайно оставался первым полем, поэтому проверка
продолжала работать и продолжала ничего не видеть. И отдел создаётся только
`if (!(await dep.count()))` — против постоянного стенда тест однажды перестаёт нажимать
форму вообще.

**Второй тест, написанный специально под эту озвучку, тоже был зелёным.** В #174 — PR того
же дня, предыдущий — добавили колонку владельца и сторож к ней — `smoke.spec.ts:694`,
«not one department names an owner», `toBeGreaterThan(0)`. Он зелен, потому что
[seed.ts:104](apps/api/src/seed.ts:104) пишет отделы IT и OPS с владельцами **сырым SQL**.
Проверка читала состояние, которое создал не продукт.

**Со стороны api поймать было нечем, и не потому, что не догадались:** дефект был целиком
на клиенте. Но заметно другое — в `departments.e2e-spec.ts` на тот момент было 12 тестов и
**слово `owner` не встречалось ни разу** (`git show 1ce0433~1:apps/api/test/departments.e2e-spec.ts
| grep -i owner` → пусто), хотя эта колонка решает, кому уходит бюджетная тревога.
Единственная проверка владельца жила в
[budgets.e2e-spec.ts:723](apps/api/test/budgets.e2e-spec.ts:723) и создавала отдел через
api, а не через форму.

**Дешевле всего:** три строки в том же тесте smoke — выбрать владельца в форме, запомнить
его id, после создания сверить значение `select` в строке таблицы с запомненным id. Именно
это теперь и стоит ([smoke.spec.ts:610](apps/web/tests/smoke.spec.ts:610)), причём в #178
проверку пришлось усилить второй раз: `not.toHaveValue('')` («вернулся хоть какой-то
владелец») проходит и у формы, которая всегда отправляет первого активного пользователя.

### Дефект 2 — `NotifyEmailer.fanOut` при заданном получателе опустошал список

**Что было.** Запрос рассылки И-склеивал два условия — `u.status = 'ACTIVE'` и
`($2::uuid IS NULL OR u.id = $2)`. Отключённый владелец отдела давал пустой список, дальше
`if (!users.length) return` — письмо не уходило никому, вместо задокументированного
расширения на организацию. Жил с 28.10.2026 (`6551e6c`) до 10.11.2026 (`1ce0433`).

**Какой тест должен был поймать.** Их два, и оба существовали.

`mail.e2e-spec.ts` — единственное место, где исходящая почта вообще наблюдаема (провайдер
подменён на собирающий список). Но все четыре его теста идут по **безадресной** ветке
(заказ поставщику, изменение заказа): `userId` там всегда `null`, то есть сломанное условие
в них не участвует.

`budgets.e2e-spec.ts:723` — «the warning is addressed to the department owner when one is
named». Название обещает адресность доставки, утверждение проверяет колонку:

```ts
const row = await db.query(
  `SELECT recipient_user_id FROM notifications WHERE type='BUDGET_THRESHOLD_CROSSED' …`);
expect(row.rows[0].recipient_user_id).toBe(ownerId); // not a blast to the whole org
```

Эта запись происходила и при сломанной рассылке. Хуже: **`recipient_user_id` не читает
никто** — `GET /notifications`
([notify.module.ts](apps/api/src/common/notify/notify.module.ts)) выбирает строки без
условия по получателю, а политика RLS фильтрует по организации. Проверка мерила колонку без
читателя и называлась проверкой адресации. Плюс в ней активный владелец — состояния, в
котором дефект проявляется, не было.

**Дешевле всего:** один тест в `mail.e2e-spec.ts` — отключить адресата в SQL, перейти порог,
убедиться, что `sent` не пуст. Десять строк, своего приложения не нужно. В #177 сделано
полнее и правильнее ([notify-recipient.e2e-spec.ts](apps/api/test/notify-recipient.e2e-spec.ts)):
проверяется и письмо, и запись о расширении в аудите, чтобы «ушло всем» и «не ушло никому»
больше нельзя было спутать.

### Дефект 3 — строка с владельцем читалась как «без владельца»

**Что было.** Условие спрашивало «статус владельца не ACTIVE» вместо «владельца нет среди
предложенных». Пока `/settings/users` в полёте (а он садится позже `/departments`), список
активных пуст, дополнительный `<option>` не рисовался, и `<select>` оставался без варианта,
совпадающего со своим значением.

**Проверено опытом** (настоящий Chromium из кэша Playwright на этой машине, сборка 1228;
`scratchpad/exp-select/case.html`):

| случай | `selectedIndex` | `select.value` | что видно |
|---|---|---|---|
| значение задано, совпадающего `<option>` нет | `-1` | `""` | ничего |
| то же, затем список вариантов перерисован (это и делает React) | `0` | `""` | **«No owner»** |
| владелец оставлен вариантом (после правки) | `1` | `"OWNER"` | «Leaving Head» |

То есть видимое «без владельца» — следствие перерисовки списка, и в обоих сломанных случаях
`select.value` становится пустым. Значит утверждение `toHaveValue(ownerId)` дефект **видит**
— если тест создаст состояние.

**Какой тест должен был поймать.** Тот самый
[department-owner-reachable.spec.ts](apps/web/tests/department-owner-reachable.spec.ts),
написанный в том же PR #175, который дефект и привёз. Он утверждает `toHaveValue(leaver.id)`
— правильное утверждение. Но делает это после того, как страница устоялась, а
автоповторяющееся `expect` по построению ждёт, пока станет правильно. Перебор состояний
(дыра №3 выше) показывает: старое и новое условие расходятся **только** при пустом `users`,
и такого состояния не создаёт ни один тест. Поэтому дефект не закрыт сторожем до сих пор.

**Дешевле всего:** `page.route` на `/settings/users` с отказом — четыре строки в уже готовом
файле.

### Дефект 4 — шаг снижения цены на аукционе не рисовался

**Что было.** `sourcing_events.auction_min_decrement_minor` существует с июля 2026, эндпоинт
отдавал его всегда
([auction.service.ts:123](apps/api/src/modules/sourcing/auction.service.ts:123)), панель
рисовала начальную цену, лучшую цену и потолок — а шаг нет. Поставщику оставалось вывести
правило из двух чисел. Жил с 05.07.2026 (`ee366d4`) до 10.11.2026.

**Какой тест должен был поймать.** Правило как правило проверено хорошо:
[auction-flow.e2e-spec.ts:89](apps/api/test/auction-flow.e2e-spec.ts:89) — «next bid must
beat best by the min decrement», сервер его держит. **Никакой тест api этот дефект увидеть
не мог**: со стороны api всё было верно, включая поле в ответе. Это чисто «есть в ответе,
нет на экране», и ловится только утверждением на экране.

Такого утверждения не было: до правки `data-testid` на панели аукциона не существовало
вовсе, а единственный браузерный тест, доходящий до неё
([evaluation.spec.ts:168](apps/web/tests/evaluation.spec.ts:168)), проверял слова («цена
подаётся живьём») и отсутствие чужих слов, но ни одного числа панели.

**Дешевле всего:** одна строка в этом же тесте — он сам создаёт аукцион с
`minDecrementMinor: 1000`, значит `toContainText('10.00')` на плитке шага. Именно это и
добавлено; в #178 проверку усилили ещё раз — подсказку проверяют нарисованной
(`::after`, `opacity`), а не по наличию атрибута.

### Что общего у четырёх

1. **Три из четырёх — на шве «экран ↔ приёмник»**, где у набора api нет глаз, а у
   браузерного набора — утверждений. №1 (поле не ушло), №3 (значение не прочиталось), №4
   (значение не нарисовалось).
2. **Два пришлись на место, где тест был и был зелёным** — потому что мерил не то: наличие
   вместо значения (№1), колонку без читателя вместо доставки (№2).
3. **Один из них привёз PR, добавлявший проверку против этого же класса ошибок** (№3): само
   по себе лучшее доказательство, что проверку надо проверять падением, а не чтением.
4. **Все четыре нашёл человек, сверявший экран с утверждением о нём** (озвучка курса).
   Тесты же почти везде сверяют экран с ним самим: «заголовок на месте», «AZN видно», «строка
   появилась». Запись курса оказалась единственным местом, где у экрана спрашивали, то ли
   он показывает, что про него говорят.

### Где тест есть, но он слабее, чем выглядит

Счёт по форме утверждений: 1 533 строки с утверждениями; 285 (18,6 %) — «правда/ложь»,
«видно», «существует», «больше нуля». В наборе api это почти всегда уместно (проверка
«строка нашлась» перед сверкой её полей), и ровно **один** тест api проверяет только код
ответа (`av-scan-missing-object.e2e-spec.ts:162`). Слабые формы собраны в браузерном
наборе: `finance` 71 %, `smoke` 51 %, `evaluation` 48 %, `analytics` 43 %. Часть из них
законна — отсутствие элемента, геометрия, раскладка. Не законны вот эти.

1. **«Страница открылась» вместо «страница показала данные».** Весь обход разделов — это
   ```ts
   async function assertRenders(page, path, headingHint) {        // smoke.spec.ts:78
     await visit(page, path);
     await expect(page.locator('h1').first()).toContainText(headingHint, { timeout: 20_000 });
     await expect(page.locator('text=Unexpected Application Error')).toHaveCount(0);
   }
   ```
   Заголовок совпал, React не упал — и так проверены 13 разделов покупателя и 7 поставщика
   (`smoke:247`, `smoke:902`). Для каталогов, логистики, верификации и реестра поставщиков
   это **вся** проверка экрана, какая есть.
2. **«Видно AZN» вместо сверки числа** — `smoke:356` (разобрано в дыре №1), и ещё три места,
   где «деньги на экране» подтверждаются присутствием кода валюты (`smoke:358`, `:552`,
   `:571`).
3. **«Вернулся хоть какой-то» вместо «вернулся тот самый»** — исходный вид проверки
   владельца в #175 (`not.toHaveValue('')`), усиленный в #178 только после того, как
   дефект уехал. Того же рода — `expect(ownerValues.filter(Boolean).length).toBeGreaterThan(0)`
   (`smoke:694`), зелёный благодаря seed.
4. **Колонка без читателя вместо доставки** — `budgets.e2e-spec.ts:723` (разобрано в дефекте
   №2). Самый дорогой вид слабости: проверка выглядит как проверка канала, а меряет побочную
   запись.
5. **Формула, пересчитанная из своих же чисел** — `budgets.e2e-spec.ts:250` и четыре
   проверки вида `remaining = amount − committed` (дыра №11).
6. **Создание «если ещё нет»** — `smoke:589` создаёт отдел только при его отсутствии, то
   есть против постоянного стенда (`BASE_URL`) форма не нажимается никогда, а проверка
   владельца под `if (justCreated)` молча выключается. В CI стенд свежий, поэтому в CI это
   работает; как проверка деплоя — нет.
7. **96 `data-testid` в интерфейсе, 36 читает хоть один тест.** Это не мера покрытия (на
   карточке тендера тесты ходят по ролям и тексту), но показательно: у
   `pages/buyer/EventDetail.tsx` 11 зацепок и ни одной используемой, у
   `pages/supplier/SupplierEvent.tsx` — 10 и ни одной, у `pages/buyer/Suppliers.tsx` — 7 и
   ни одной. Зацепки ставили под проверки, которых не написали.

### Что, наоборот, сильнее, чем принято ожидать

Честности ради — это не набор, который надо переделывать:

- **Изоляция на уровне БД** (`rls-acl`, 19 тестов): чужая организация видит 0 строк,
  подделанная строка отклоняется, суммы закрыты до вскрытия, аудит только дописывается.
- **Счета и бюджеты** проверены по обе стороны и в трёх языках, вместе с гонками ответов и
  упавшими списками — это редкость.
- **Пояса и календарные дни** (`invoice-issue-date` 11, `date-columns` 6,
  `document-no-year` 8) — проверки, которые держат класс ошибок, а не случай: в
  `date-columns` часы переводят на Asia/Baku внутри самого спека, чтобы сторож работал и на
  раннере в UTC.
- **Утверждения с объяснением в самом `expect`** (`'not one department names an owner'`) —
  падение сразу говорит, что сломалось.
- **Проверки, проверенные падением.** В #178 про три усиленных сторожа прямо сказано:
  «каждый проверен падением». Это ровно та дисциплина, которой не хватало в #174 и #175.

## 3. Нужен ли здесь Maestro

**Нет.** Не нужен, и дыры из этого документа он не закрывает ни одной.

Maestro водит нативное приложение по дереву доступности устройства — это его работа, и для
MTMobileApp он на месте. Leadprocure — веб: React + Vite, который открывают в браузере на
рабочей машине. Браузерный набор уже на Playwright, и то, чего здесь не хватает, — это
ровно те вещи, которые Playwright умеет, а Maestro не умеет:

| Что нужно по этому аудиту | Playwright | Maestro |
|---|---|---|
| Уронить или задержать один запрос (`/settings/users`) — дыры №3 и №7 | `page.route` | нет |
| Сверить тело запроса и ответа с тем, что ввели (дефект №1, дыра №4) | `waitForResponse`, `request` | нет |
| Прочитать вычисленный стиль и `::after` (подсказка нарисована, а не объявлена) | `evaluate` | нет |
| Две роли в одном сценарии, два контекста, свои cookie | `browser.newContext` | нет |
| Прогон без человека и без устройства в GitHub CI | да | нужен телефон и adb |
| Ширины 1440/1280/1024/768/375 за один визит | `setViewportSize` | только то, что у устройства |

Единственное, что Maestro мог бы добавить, — это прогон по Chrome на настоящем телефоне. Но
дыра здесь не в достоверности отрисовки: экран на 375 px и так проверяется на двадцати
страницах и пяти ширинах, и падает он не из-за отличий настоящего Android от эмуляции
размера. Дыра в утверждениях — в том, что их нет там, где нужно. Инструмент этого не
исправляет.

И практическое: приёмка Leadprocure обязательна на каждом PR и идёт без человека. Потоки
Maestro на телефоне владельца требуют его открытого туннеля adb и его же телефона на
переднем плане — так устроена проверка MTM, и это сознательно ручная процедура. Обязательной
проверкой такое сделать нельзя.

Если когда-нибудь появится мобильное приложение Leadprocure — Maestro пригодится там, и
опыт MTM перенесётся без переделки. Для веб-части ответ останется тем же.
