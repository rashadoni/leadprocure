# Как переснять видео-подсказки разделов

У каждого раздела своя запись: `apps/web/public/guides/<ключ>.az.webm` плюс постер
`.az.png`. Карта «маршрут → ключ» — `apps/web/src/guides.ts`, сценарии и комбайн —
`scripts/produce-guides.mjs`. Записи **только азербайджанские** (решение владельца
01.11.2026): `Guide.tsx` просит `.az` при любом языке интерфейса.

## Где это можно запускать

Съёмка — это живой стенд, браузерный прогон 22 разделов и за две сотни запросов к
синтезу речи. Нужна машина, где есть **Docker, Node 20+, pnpm 10.33.4**, и где не жалко
~10 ГБ под образы и тома.

По умолчанию это **не Contabo**: правила хоста запрещают там полные сборки, браузерные
прогоны и установку зависимостей. Но 01.11.2026 владелец разрешил этот прогон именно на
боксе, и он прошёл там без единой сборки образа — потому что на боксе уже лежали
`postgres:16`, образ MinIO и готовый `leadprocure-api` от сборки CI. Стенд встал за
полминуты. **Это и есть вопрос, который стоит задать до выбора машины**: нужные образы
уже есть? Если да, бокс обходится дешевле Мака, где всё тянется с нуля (там сборка MinIO
из исходников одна заняла двадцать минут). Запуск на Contabo остаётся решением
владельца под конкретную задачу, а не правилом по умолчанию.

**Как не собирать образы, если они уже есть.** `infra/docker-compose.demo.yml` нарочно
собирает оба образа из исходников: образ хранилища — из закреплённого upstream
(`infra/storage`, цепочка поставки), API — из чекаута. Для одноразового стенда на машине,
где нужные артефакты уже лежат, это ~25 минут и ничего не даёт. Подменяется **локальным,
не коммитимым** override-файлом рядом (`docker compose … -f infra/docker-compose.demo.yml
-f <override>.yml`):

```yaml
services:
  leadprocure-demo-minio:
    image: minio/minio:latest        # прод крутит тот же образ
    build: !reset null
    pull_policy: missing
  leadprocure-demo-createbuckets:
    image: minio/mc:latest
    pull_policy: missing
    entrypoint: ["/bin/sh", "-c"]
    command: ["<те же три шага, что infra/storage/bootstrap-bucket.sh: дождаться адреса, mc mb --ignore-existing, mc anonymous set none>"]
  leadprocure-demo-api:
    image: leadprocure-api:<sha текущего main>   # docker images | grep leadprocure-api
    build: !reset null
    pull_policy: never
```

В коммит это не идёт: в репозитории сборка из исходников — осознанное решение, а подмена
на `:latest` годится только для выбрасываемого стенда на доверенной машине. **Проверяйте,
что sha образа соответствует коду, который снимаете** — иначе снимете прошлую версию
интерфейса и не заметите.

## Один раз на машине

```bash
git clone https://github.com/rashadoni/leadprocure.git && cd leadprocure
git lfs install && git lfs pull        # записи лежат в LFS, без этого придут указатели
pnpm install --frozen-lockfile
pnpm --filter web exec playwright install chromium
```

**Шрифт эмодзи — на машине съёмки он обязателен, и его отсутствие не ломает прогон, а
портит все записи.** В интерфейсе эмодзи стоит почти на каждой кнопке (🔒 RFQ,
🌐 «Açıq tender», 🕘 «Tarixçə», 📅 «Aylar üzrə bölgü», 🗑 «Sil», 📦 «Birbaşa sifariş»,
🔎 в поиске). Без шрифта Chromium рисует на их месте пустой прямоугольник — запись
выглядит так, будто в продукте сломаны символы, хотя у владельца на Маке всё на месте.
Символы из основной плоскости (⚡ ⚖ ⤓ ↪ ✎ ✕) берутся из Noto Sans и рисуются всегда,
поэтому беглым взглядом по логу подмена не видна — только глазами по кадру. Ставить
по-пользовательски, без sudo:

```bash
mkdir -p ~/.local/share/fonts/noto
curl -sSL -o ~/.local/share/fonts/noto/NotoColorEmoji.ttf \
  "$(curl -sS -A 'Mozilla/5.0' 'https://fonts.googleapis.com/css2?family=Noto+Color+Emoji' \
     | sed -n 's/.*url(\(.*\)) format.*/\1/p')"
fc-cache -f ~/.local/share/fonts
fc-list | grep -ci emoji        # должно быть не 0
```

Ссылку брать из CSS API, а не из GitHub: `raw.githubusercontent.com` на
`noto-emoji` отдаёт HTML-страницу, и `curl -o` молча кладёт её под именем
`.ttf` — `file` потом говорит `HTML document`, а `fc-cache` просто
игнорирует файл.

Ключи синтеза речи — в корневой `.env` репозитория (он в `.gitignore`, в git его нет):

```
AZURE_SPEECH_KEY=…
AZURE_SPEECH_REGION=…
GEMINI_API_KEY=…
```

Для азербайджанского нужен **`GEMINI_API_KEY`**: `ENGINE.az = 'gemini'` (решение
владельца — озвучка из Google AI Studio). У Azure азербайджанский голос тоже есть
(`az-AZ-BanuNeural`, включается `TTS_AZ=azure`), но на слух признан слабым. Можно положить
несколько ключей (`GEMINI_API_KEY2`, `…3`): при дневной квоте скрипт сам переходит к
следующему.

**Суточная квота — главное ограничение, и считается она в запросах, а не в минутах.**
Google отказывает с 429 и называет метрику; скрипт теперь печатает её имя
(`GenerateRequestsPerDayPerProjectPerModel`), а не выводит «daily cap» из того, что в теле
ответа где-то встретилось слово `PerDay`. Разница не теоретическая: 429 по МИНУТНОМУ лимиту
читался точно так же, и прогон, которому надо было подождать минуту, вместо этого сжигал
все ключи по очереди. Сбрасывается квота в полночь по тихоокеанскому времени (в Баку —
**не в полночь, а по скользящему окну** — см. ниже). Лимит на 02.11.2026 — **100 запросов в сутки на модель на проект**
(ответ Google: `generate_requests_per_model_per_day, limit: 100`). 22 раздела — это
около 228 сцен, то есть **на двух бесплатных ключах полная пересъёмка в один день не
влезает по арифметике**: 200 против 228. Ровно это и произошло 01.11.2026 — 16 разделов
прошли, два последних остались. Планируйте два дня или держите третий ключ.

**Окно скользящее, и Google сам говорит, когда пробовать.** Не «сбрасывается в полночь»:
в теле 429 есть строка `Please retry in 23h52m…`, и 02.11.2026 оба ключа назвали почти
ровно 24 часа — то есть ждать надо сутки от прогона, а не до ближайшей полуночи. Это стоило
дня: съёмка была поставлена на полночь по тихоокеанскому и в 00:02 получила тот же отказ.
Читайте `retry in` из ответа вместо того, чтобы вычислять время самостоятельно.

Это, кстати, **Tier 1** — платный проект. Сто в сутки здесь не признак бесплатного
тарифа, а потолок самой модели, и доплатой он не снимается: нужен либо ещё ключ (другой
проект — своё ведро), либо запрос на повышение квоты в консоли Google. Модель с датой в
имени, у которой было бы своё ведро при том же голосе, у `gemini-3.8-flash-tts` отсутствует
— в списке моделей есть только `2.5-*-preview-tts`, `3.1-flash-tts-preview`,
`3.8-flash-tts` и `3.8-flash-lite-tts`, и у каждой свой голос на слух. Менять модель ради
квоты нельзя: голос двух разделов разойдётся с остальными шестнадцатью.

Сколько запросов реально нужно — считается до прогона, по кэшу: ключ кэша это
`sha256("gemini-<голос>|<язык>|<текст>")`, первые 32 символа, файл
`scripts/.tts-cache/<ключ>.mp3`. После прерванного прогона часть сцен уже озвучена, и
досъёмка может оказаться втрое дешевле, чем кажется по числу сцен.
Озвучка кэшируется (`scripts/.tts-cache`), поэтому повторный прогон уже снятого раздела
бесплатен — этим и стоит проверять любую правку самого комбайна.

**Недействительный ключ в `.env` страшнее кончившейся квоты.** 401/403 — это не «ключ
занят», а «ключа нет», и скрипт теперь выбрасывает такой ключ сразу и идёт к следующему.
Раньше он считал 401 временной ошибкой, десять раз повторял с нарастающей паузой и через
полторы минуты ронял весь прогон — при двух живых ключах, которые могли бы его закончить.

Модель по умолчанию — `gemini-3.8-flash-tts`, голос **Kore**, язык передаётся **явно**
северным `az-AZ`. **И модель, и голос выбрал владелец на слух** 01.11.2026, сравнив три
пробы одной и той же азербайджанской фразы (3.8-flash, 3.8-flash-lite, 2.5-preview). Менять
их без того, чтобы дать ему послушать замену, нельзя. Язык задавать обязательно: Google перечисляет азербайджанский дважды, и
южный (иранский) — другая норма и другое письмо, для Баку он прозвучит неправильно.
Модель меняется через `GEMINI_MODEL`; учтите, что 3.8 отвечает контейнером `audio/wav`, а
2.5-preview — сырым L16, и скрипт различает это сам.

### Сначала проба, потом все записи

Голоса Gemini не привязаны к языку — один голос говорит на всех, и как он звучит именно
по-азербайджански, из документации не узнать. Поэтому **сначала одна короткая проба**, и
дать её послушать владельцу:

```bash
FORCE=1 GUIDES_PG_CONTAINER=<контейнер postgres стенда> GUIDES_DB=<база стенда> node scripts/produce-guides.mjs http://localhost:5173 az buyer-requests
```

Это первая глава истории (9 сцен) — и единственная, которую можно снять первой, потому что
остальные опираются на её данные. Голос и модель уже одобрены на пробах, так что проба
нужна не для выбора голоса, а чтобы увидеть всю цепочку целиком: встал ли стенд, попадает
ли голос в кадр, не видно ли строки подсказки, нет ли мёртвых пауз. Если что-то не так —
чинить до того, как уйдут остальные.

**`GUIDES_PG_CONTAINER` и `GUIDES_DB` обязательны для любого прогона.** Без них съёмщик
отказывается на первой строке: ему нечем проверить ни что глава не создаст вторую строку с
тем же названием, ни в какой точке истории стоит стенд. Имя базы должно кончаться на
`_guides`, `_demo` или `_walkthrough` — это единственное, что отделяет запись роликов от
боевой базы.

## Съёмка

```bash
bash scripts/demo-stand.sh
```

Скрипт поднимает одноразовый стенд, прогоняет миграции, сеет учётки и наполняет
демо-историю **по-азербайджански** (`DEMO_LANG=az` — сценарии кликают по названиям вида
«Tender: noutbuk və monitorlar», на другом языке эти клики промахиваются), затем печатает
две команды. Веб-фронт поднимается отдельно, потому что адрес API вшивается на сборке:

```bash
VITE_API_BASE_URL=http://localhost:3200 pnpm --filter web dev
```

**`localhost` с обеих сторон — обязательно, и это не придирка.** Refresh-кука ставится с
`SameSite=lax`, а для браузера `localhost:5173` и `127.0.0.1:3200` — разные сайты. Куку он
на такой запрос не пошлёт, `/auth/refresh` ответит 401, и **каждая** полная загрузка
страницы будет выбрасывать на экран входа. Съёмка как раз и делает полную загрузку на
каждом разделе, так что запись выйдет из двадцати двух экранов логина.

```bash
FORCE=1 GUIDES_PG_CONTAINER=<контейнер postgres стенда> GUIDES_DB=<база стенда> node scripts/produce-guides.mjs http://localhost:5173 az
```

Без ключей снимается ВЕСЬ курс в порядке истории (`ORDER` в съёмщике) — это и есть
основная форма. `FORCE=1` обязателен для пересъёмки: без него скрипт **пропускает**
разделы, у которых файл уже есть (это поведение «продолжить прерванный прогон»).

**Одну главу посреди истории переснять нельзя, и это запрещено намеренно.** Стенд ведёт
список снятых глав, и глава отказывается сниматься, если на стенде уже сняты поздние: иначе
в кадр попадают данные, о которых её озвучка не говорит. Так однажды глава про бюджеты
показала 78,7% под слова «тридцать восемь процентов». Правильный путь — пересеять стенд и
снять всё подряд; `ALLOW_STALE_STAND=1` снимает запрет для главы, числа которой от
положения стенда не зависят, и громко об этом пишет.

После прогона стенд убрать: `bash scripts/demo-stand.sh down`.

### Стенд датирован — он протухает примерно за неделю

`demo-fill` ставит сроки **относительно наполнения**, и сроки эти разные:

| где в `demo-fill.mjs` | срок | что это |
|---|---|---|
| 396 | +4 дня | аукцион «ofis kağızı» |
| 522, 547, 559 | +7 дней | тендер на мебель, запрос сведений, тендер под каталог |
| 381 | +8 дней | «живой» тендер на ноутбуки |
| 162 | закрывается сразу | тендер, который должен прийти уже присуждённым |

Поэтому стенд, убранный сразу после прогона, как велит строка выше, не протухает никогда.
Протухает оставленный работать: на четвёртый день закрывается аукцион, на седьмой — почти
всё остальное, на восьмой — последний тендер.

**Сверяя это с живым стендом, помните, что его могли править руками.** На стенде, который
стоит с 2 ноября, аукцион показывает срок 9 ноября 23:34, а не 6-го, как дают его четыре
дня: 6 ноября он закрылся посреди пересъёмки, и срок продлили вручную, чтобы доснять
раздел. Все шесть событий при этом созданы одним наполнением, 2 ноября в 08:22, — два
разных срока в таблице это не два дня заливки, а +7 и +8 дней от одного.

**Этого сторожа больше нет, и правильно.** Он требовал, чтобы на стенде УЖЕ лежало
открытое событие с таким-то названием, — это был мир заранее залитых данных. История
создаёт их сама, требование сняли со всех разделов, и сторож стал выходить на первой
строке, продолжая утверждать комментарием, что работает. На его месте — `CREATES`:
глава объявляет, какие строки она СОЗДАЁТ, и прогон отказывается, если они на стенде уже
есть. Проверить нечем (не переданы `GUIDES_PG_CONTAINER` и `GUIDES_DB`) — тоже отказ.
Причина та же, что была у прежнего сторожа, только с другой стороны: сцена ищет свою
строку как `tr:has-text("<название>")` и берёт первую, поэтому второй тендер с тем же
именем снимется молча и не тот.

**И отдельно — образ API на стенде должен быть тем кодом, который снимают.** Веб-фронт
идёт `vite`-ом из рабочего дерева и всегда свежий, а API — контейнер, то есть образ той
версии, на которой стенд подняли. 07.11.2026 стенд работал на `leadprocure-api:4c65cf1e`
от 2 ноября, а снимали код `94aa8fe`: карточка заказа (#110) уже умела показывать цепочку
«заказ → контракт → тендер», но старый API отдавал `contract_no` пустым, и сцена про эту
цепочку сняла бы пустое место. Видно это только глазами — ни промаха курсора, ни
предупреждения. Сверять так:

```bash
docker inspect leadprocure-demo-api --format '{{.Config.Image}}'   # и сравнить с git log -1
```

Если образ отстал, пересобирать не нужно: CI уже собрала образ текущего `main`
(`docker images | grep leadprocure-api`), и его подставляют тем же локальным
override-файлом, что и в разделе выше, одной командой
`docker compose -p leadprocure-demo -f infra/docker-compose.demo.yml -f <override>.yml up -d
--no-deps leadprocure-demo-api`. Данные стенда это не трогает: миграции в entrypoint
идемпотентны, а сид и наполнение туда не входят.

Поэтому перед пересъёмкой: либо поднять стенд заново, либо посмотреть, что на нём
осталось живого.

```bash
docker exec leadprocure-demo-pg psql -U leadprocure_owner -d leadprocure_demo -At -F' | ' \
  -c "SELECT title, status, to_char(close_at,'MM-DD HH24:MI'), close_at > now() FROM sourcing_events ORDER BY close_at;"
```

Если ближайший срок уже прошёл или наступит в ближайшие сутки — пересеивать, а не
продлевать по одному событию: продление чинит тот раздел, который отказал, и оставляет
четырнадцать, которые не отказывали.

## Селекторы — проверять ДО того, как тратить квоту

Промах селектора стоит суточной квоты: прогон отработает, запишет видео, озвучит его — и
всё это по неподвижному экрану. Поэтому перед прогоном стоит прогнать сценарии «на сухую»:
коротким скриптом Playwright открыть нужные страницы и посчитать, что каждый селектор
что-то находит. Это не стоит ни одного запроса к синтезу.

**Ловушка, которая выглядит как сломанный сценарий**: такой проверочный скрипт обязан
выставить язык так же, как это делает комбайн —
`ctx.addInitScript((l) => localStorage.setItem('lp_lang', l), 'az')` **до** первой
страницы. Без этого стенд открывается по-русски, и каждый азербайджанский текстовый
селектор честно не находит ничего: «Auksion» против «Аукцион». Половина селекторов
аукциона так и «промахнулась» 02.11.2026 — сломан был проверочный скрипт, не сценарий.

**Поле формы адресовать по подписи, а не по порядку.** `form input` nth(0) значит
«какой инпут сегодня первый»: добавят поле выше — и курсор молча наберёт название плана в
графу категории. Промахом это НЕ станет, селектор по-прежнему что-то находит, в логе чисто,
и единственный след — неверное слово на экране в уже готовой записи. То есть это хуже
промаха: промах теперь печатается, а это нет. В комбайне для таких случаев `budField()`
(`form div:has(> label:has-text(…)) input`), в браузерных тестах — `data-testid`
(AGENTS.md про ту же ловушку на той же форме). Проверять подстановкой: набрать значение в
одно поле и прочитать соседние — они должны остаться прежними.



Записи длинные и их 20, поэтому смотреть выборочно, но обязательно:

1. **Строки подсказки нет в кадре.** Скрипт прячет `[data-help-video-widget]`, чтобы
   подсказка не попала в запись самой себя. Если строка видна — селектор разошёлся с
   разметкой `Guide.tsx`.
2. **Нет мёртвых пауз.** Сцена, чьи действия длиннее озвучки, пишет в лог
   `⏱ <ключ>/az сцена N: действия дольше озвучки на Nс`. Логи прогона смотреть целиком.
3. **Курсор не стоит на месте всю сцену.** Значит селектор не нашёлся. Раньше это было
   видно только глазами: `moveTo` возвращал `false`, сценарии его не проверяют, и промах
   выглядел как пауза, которую рассказ оставил нарочно. Теперь каждый непойманный элемент
   печатается как `✗ <ключ>/az сцена N: цель не найдена — <селектор>`, а в конце прогона
   стоит итог `промахов курсора: N`. Сценарий, который сам бросает исключение, по-прежнему
   печатается как `(<ключ>/az: <сообщение>)`.
4. **Постеры.** `<ключ>.az.png` снимается до появления курсора; он красит первый кадр
   внутри окна плеера — и с PR #95 он же стоит кадром 72×40 в самой строке подсказки,
   так что промахнувшийся или пустой постер виден теперь не только в плеере.
5. **Голос попадает в кадр**, а не отстаёт: озвучка начинается на границе сцены, курсор
   идёт следом с задержкой `LEAD = 650 мс`.
6. **Длительность сверяет сам прогон.** В конце каждой записи скрипт меряет готовый файл
   `ffprobe`-ом и сравнивает с тем, что раздел «Обучение» обещает — с `sec` соответствующего
   урока в `COURSE` (`apps/web/src/guides.ts`). Расхождение больше двух секунд — громкий
   отказ с названием ключа и обоими числами, прогон падает. Проверяется только `az`: `sec`
   мерялся по азербайджанским файлам, и ru/en той же меркой мерить нечестно. У ключа,
   которого в курсе ещё нет, сверять не с чем — скрипт просто печатает
   `↳ в курсе этого урока ещё нет — объявить sec: N`, и это число идёт в `COURSE` вместе с
   самой записью. Зачем: `sec` пишется руками, а обрезанную пересъёмку больше никто не
   заметит — постер на месте, видео отдаётся, тесты зелёные, и ошибается только зритель,
   которому обещали четыре минуты. Замечание пришло из разбора PR #121, и место ему именно
   там, где файл рождается.
7. **Глазами по готовой записи — контактным листом.** Шесть проверок выше спрашивают, верно
   ли СНЯЛОСЬ. Ни одна не спрашивает, верно ли работал продукт в кадре, — а это отдельный
   класс, и он доезжает до пользователя. 07.11.2026 владелец смотрел `buyer-budgets` и на
   2:16–2:29 увидел редактор «Aylar üzrə bölgü», открытый на красном `Cəmi: 99.99%` с
   погашенной кнопкой: доля месяца по умолчанию считалась `Math.round(10000/n)`, и у
   трёхмесячного периода 3333×3 давало 9999 (исправлено в #131). У той записи было ноль
   промахов курсора, ни одной мёртвой паузы, сходящаяся длительность и зелёная приёмка.
   Найти это мог только глаз.

   Смотреть всё целиком — это час с лишним, поэтому раскладывайте запись контактным листом:
   кадр раз в несколько секунд, уменьшенный, с выжженным временем, плиткой. Минута на
   запись, и дефект вроде красной строки виден на развороте не читая.

   ```bash
   K=sup-catalogs && ffmpeg -nostdin -y -i "apps/web/public/guides/$K.az.webm" \
     -vf "fps=1/10,scale=640:360,drawtext=text='%{eif\:n*10\:d}s':x=8:y=8:fontsize=22:fontcolor=yellow:box=1:boxcolor=black@0.6,tile=3x4" \
     "/tmp/$K-%d.png"
   ```

   Ключ — в переменную, а не в угловые скобки: `<ключ>` zsh читает как перенаправление
   ввода и отвечает `no such file or directory`. Шаг `1/10` — компромисс: сцены в этих
   записях идут от 4,5 до 25,7 секунды при медиане 17,7, то есть самая короткая может
   провалиться между кадрами. Для беглого просмотра этого хватает, для внимательного
   ставьте `fps=1/5`. По сцене ровно кадр не нарежешь: границы сцен известны прогону, но
   никуда не сохраняются.

## Трафик LFS, а не место: что приёмка качает на каждом прогоне

**Потолки — 10 GiB хранилища и 10 GiB трафика в месяц** на планах Free и Pro; проверено
02.11.2026 по живой странице
[docs.github.com/billing/concepts/product-billing/git-lfs](https://docs.github.com/en/billing/concepts/product-billing/git-lfs).
Прежняя редакция этого раздела говорила «1 ГБ и 1 ГБ» и предрекала, что следующая
пересъёмка в склад не влезет — **это было неверно в десять раз**. Предоплаченных «пакетов
данных» больше нет вовсе, оплата поштучная. Если здесь снова появится цифра — сверяйте её
с той страницей, а не с этим файлом.

**Место тратит `git push`, а не мерж.** Объекты уезжают в хранилище при пуше, и GitHub
считает их по РЕПОЗИТОРИЮ, а не по веткам: закрыть PR или переписать историю места не
вернёт. Проверять `git lfs push --dry-run origin <ветка>` — пусто значит всё уже там.
`git lfs ls-files --all` при этом ЗАНИЖАЕТ: он видит только ссылки, которые есть в клоне.
На 02.11.2026 по всем веткам `origin` — 534 объекта на 956 783 489 байт, то есть 0,89 GiB,
около 9 % хранилища. Запаса хватает на десятки пересъёмок; полная добавляет ~0,16 GiB.

**Дорог трафик, и считается только скачивание.** `actions/checkout` тянет объекты
выложенного коммита, а не весь склад: 164 МБ видео плюс 1,5 МБ постеров. Пока в обеих
джобах `acceptance.yml` стоял `lfs: true`, один прогон PR стоил ~320 МБ — около
тридцати прогонов в месяц, достижимо за неделю активной работы. Без привязанной карты
исчерпанный трафик выключает LFS до первого числа следующего месяца.

**Поэтому приёмка больше не качает видео** (решение владельца 02.11.2026). В обеих джобах
`lfs: false` плюс `git lfs pull --include="apps/web/public/guides/*.png"`: ни один тест
видео не упоминает, а строка подсказки проверяется одинаково с записями и без них. Прогон
стоит единицы мегабайт вместо 320. Видео нужно только упаковке релиза.

**Постеры после этого обязаны проверяться, иначе правка оставляет тихий зелёный.** Раз
качаются только они, приёмка на них и смотрит: в `smoke.spec.ts` к проверке строки
подсказки добавлено, что `.help-thumb img` видна и её `naturalWidth` больше нуля. У
указателя LFS, отданного под видом PNG, `naturalWidth` равен нулю; виджет по `onError`
убирает кадр, и строка молча возвращается к прежнему виду — ровно то, что `lfs: true`
прикрывал собой, ни разу не будучи проверенным. Утверждение сверено с двух сторон: на
настоящих постерах проходит, на подменённом указателем падает.

## Правила, которые нельзя нарушать

- **Один контекст браузера на роль.** Переиспользование одного `storageState` между
  контекстами повторно предъявляет провёрнутый refresh-токен и срабатывает защита от
  кражи сессии. Это сделано нарочно.
- **Длину задаёт рассказ, а не таймер.** Сначала измеряется озвучка каждой сцены, потом
  блок держится ровно столько. Не переделывать в «пауза N секунд»: беты внутри сцены —
  доли озвучки (`h.holdUntil(0.4)`), поэтому фраза другой длины всё равно попадает.
- **`demo-fill.mjs` только на одноразовый стенд.** Он зовёт `assertDemoTarget` на самом
  верху модуля, без флагов, и отказывает всему, что не помечено как disposable.
  `infra/DEPLOY.md` запрещает демо-сид на проде первой же строкой.
- **Селекторы сценариев**: `data-testid` → собственный текст заголовка или кнопки →
  позиционный только там, где порядок колонок закреплён браузерными тестами. Перед
  правкой сверять текст со словарём `az` в `apps/web/src/i18n.tsx`, а порядок ячеек
  читать из JSX, а не угадывать.
- **Сцены МЕНЯЮТ стенд, и это замысел.** Здесь стояло обратное правило — «действия в
  сценариях не должны менять стенд», — и оно было верным для экскурсии: двадцать записей
  шли по одним заранее залитым данным, и след одной был виден в остальных. История
  устроена наоборот: след предыдущей главы — это и есть то, что снимает следующая. Правило
  теперь такое: **глава меняет стенд только вперёд по своей же истории**, в том порядке,
  который объявлен в `ORDER`, и ничего не ломает за собой. Сцена, которая что-то создаёт,
  помечается `must` и берёт цели строгими помощниками — иначе промах тихо лишит данных все
  следующие главы.
- **Логистика теперь с приёмкой.** Раньше здесь стояло «на странице ноль кнопок, не
  починять выдуманным нажатием» — и для самой доски грузов это по-прежнему так. Но глава
  на ней не кончается: она уходит в «Договоры» и принимает товар, потому что принимают не
  груз, а позиции заказа, и озвучка это говорит прямо.
- **В воркитри нет своего `.env`.** Скрипт читает ключи из `.env` в корне ТОГО дерева,
  откуда запущен, и в рабочем дереве его нет — прогон падает с `GEMINI_API_KEY not set`
  при живых ключах в основном чекауте. Лечится симлинком: `ln -s <основной
  чекаут>/.env .env` (файл в `.gitignore`).
- **`TMPDIR` на другом томе.** Готовый файл раньше переносился `rename`, а это не работает
  между файловыми системами: прогон падал с `EXDEV` ПОСЛЕ того, как запись и сведение
  уже оплачены. Исправлено на копирование, но если увидите `EXDEV` где-то ещё — причина
  та же.

## Статус оснастки

`infra/docker-compose.demo.yml` и `scripts/demo-stand.sh` **отработали вживую** 01–02.11.2026
на боксе: стенд поднялся, миграции прошли, учётки засеялись, демо-история наполнилась, и
против этого стенда снято 17 разделов. `assertDemoTarget` стенд принимает и по-прежнему
отказывает прод-адресу, чужому порту, снятому флагу изоляции и контейнеру без метки.

Что первый живой прогон всё-таки потребовал починить (уже исправлено, но знать полезно):

- **`compose up --wait` без healthcheck ждёт только «контейнер запущен».** Миграции идут в
  entrypoint API, то есть контейнер работает задолго до того, как начинает отвечать, и сид
  падал с `relation "organization_users" does not exist` — выглядит как сломанная миграция,
  а на деле гонка. Теперь у API есть healthcheck, и сверх того `demo-stand.sh` сам ждёт
  `/health` перед сидом.
- **`demo-fill.mjs` разрешал отгрузку шире, чем API.** Фильтр брал любой заказ, а
  `SHIPPABLE_PO` на сервере уже сузился, и наполнение падало на 400 «The order is ACCEPTED».
- **Образ MinIO собирался из исходников.** На машине, где его нет, это двадцать минут; на
  боксе он уже был. Перед выбором машины см. «Где это можно запускать».

## Сквозная история вместо экскурсии (решение владельца 09.11.2026, снято 09.11.2026)

Владелец: «делай примерами, как будто работник начинает работать над этой системой, от
начала до конца, с реальными примерами — создавай, подтверждай, открывай саплаером и там
продолжай флоу, открывай как прокюрментом то же самое, и финансистом. Без воды и не слишком
медленными».

Это другой замысел, а не другие тексты. Прежние двадцать записей — экскурсия: каждая
показывает свой экран и живёт сама по себе. Новые двадцать две — **одна закупка, проведённая
на камеру от заявки до оплаты**, плюс разделы «про устройство», снятые на её же данных.
Ничего не инсценировано: каждое действие совершается в интерфейсе, и всё, что видно в кадре,
лежит в базе стенда после прогона.

**Записи азербайджанские, и только.** Решение владельца 01.11.2026 в силе: виджет подсказки
всегда грузит `.az`, какой бы язык интерфейса ни был выбран (`components/Guide.tsx`), и
русских с английскими файлов в `public/guides` нет. Съёмщик умеет `ru` и `en`, но тратить на
них синтез незачем, пока продукт их не читает.

### Кто играет

| роль в съёмщике | учётка | кто это в истории |
|---|---|---|
| `requester` | `user@acme.test` | новый сотрудник, отдел OPS — заводит заявку |
| `approver` | `approver@acme.test` | согласующий, владелец бюджета IT — утверждает |
| `buyer` | `admin@acme.test` | закупщик — тендер, вскрытие, присуждение, заказ |
| `sup` | `seller@supply-one.test` | поставщик-победитель — ставка, отгрузка, счёт |
| `sup2` | `seller@baku-metal.test` | второй поставщик — его ставка делает тендер тендером |
| `finance` | `finance@acme.test` | финансист — бюджет и аналитика |

Сцена переключает исполнителя полем `as`; идущие подряд сцены одного актёра пишутся одной
подзаписью, подзаписи склеиваются `ffmpeg -f concat -c copy`, а смещения звука сдвигаются на
длительность предыдущих. Так снят один экран двумя людьми: заявку заводит сотрудник,
утверждает согласующий. Рекорд — глава про аукцион: шесть прогонов, пять актёров.

### Что именно происходит в кадре

Данные одни на всю историю и объявлены один раз — `STORY` в `scripts/produce-guides.mjs`.
Числа подобраны так, чтобы ни одна глава не показывала чепухи: смета 64 000 ₼ выше порога
прямого заказа (50 000 ₼) и потому идёт тендером, но умещается в квартальный план отдела
(150 000 ₼); ставка победителя ниже сметы ровно настолько, чтобы экономия была видимой
цифрой (58 000 ₼, экономия 6 000 ₼ — её потом читают витрина, аналитика и панель).

Сквозная часть, тринадцать глав, в этом порядке:

1. `buyer-requests` (requester → approver) — заявка: название, категория, отдел, позиции;
   сервер считает итог; автор не может утвердить сам себя; согласующий видит влияние на
   бюджет и утверждает в два клика.
2. `buyer-events` (buyer) — «Elan et» → закрытый тендер, приглашение обоих поставщиков,
   публикация.
3. `sup-market` (sup) — приглашение в витрине, карточка тендера без сметы покупателя.
4. `sup-bid` (sup → sup2) — две запечатанные ставки, 58 000 и 61 000.
5. `buyer-opening` (buyer) — срок истёк, вскрытие, взвешенная оценка, ИИ-ранжирование,
   присуждение с письменным обоснованием.
6. `buyer-contracts` (buyer) — договор из присуждения, заказ по договору, отправка заказа.
7. `sup-orders` (sup) — подтверждение, перевозчик и номер отслеживания, упаковка, отгрузка,
   доставка.
8. `buyer-logistics` (buyer) — доска грузов, два статуса рядом, приёмка товара.
9. `sup-invoices` (sup) — счёт на принятое, срок оплаты.
10. `buyer-invoices` (buyer) — трёхсторонняя сверка, утверждение, оплата.
11. `buyer-budgets` (finance) — как покупка легла в план отдела: 58 000 из 150 000, темп.
12. `buyer-analytics` (finance) — расход, экономия, разрезы, год к году.
13. `buyer-dashboard` (requester) — тот же новый сотрудник видит, чем кончилась его заявка.

Разделы «про устройство» снимаются ПОСЛЕ и работают с её данными: `buyer-suppliers` (реестр,
второй поставщик добавляется в него на камеру), `sup-verification` и `buyer-verification`
(поставщик кладёт два документа, покупатель принимает), `buyer-catalogs` и `sup-catalogs`
(каталог из договора и заказ по согласованной цене), `sup-contracts`, `sup-dashboard`,
`buyer-settings` (правила, по которым всё предыдущее произошло) и `sup-auction` — вторая,
короткая история целиком: своя заявка, своё утверждение, живые торги в три шага цены.

Двадцать две записи — 26,6 минуты. Прежние двадцать шли 62: «без воды» это правило
сценария — одна сцена, один факт; то, что видно на экране, словами не повторяется; действие
начинается с первой секунды сцены.

### Промах в сцене, которая создаёт данные, обрывает прогон

В экскурсии промах стоил одну неподвижную сцену. В истории он стоит всё, что снимается
после: если заявка не создалась, объявлять тендером нечего. Поэтому сцена, которая ДЕЙСТВУЕТ,
объявляет `must: true` и берёт цели через `need` / `needClick` / `needFill` / `setDate`.
Обрыв называет главу, номер сцены и то, чего не хватило на экране; уже снятые главы при этом
сводятся и остаются на диске. Сцена может проверять и собственную озвучку: там, где голос
говорит «у автора заявки кнопки утверждения нет», прогон обрывается, если она там есть.

Раздел может объявить `before` — подготовку стенда. Она только для того, чего нельзя сделать
быстрее времени: срок тендера сутки, и `buyer-opening` переводит его в прошлое, после чего
закрывает тендер ТОЙ ЖЕ функцией `close_due_events()`, что и расписание. Имя базы обязано
кончаться на `_guides`, `_demo` или `_walkthrough`, иначе `standSql` отказывает.

### Как это запускают

Стенд: API и vite против ОТДЕЛЬНОЙ базы, залитой `pnpm --filter api seed`, и MinIO с
бакетом, который назван в `S3_BUCKET`. **Бакет надо создать** — его отсутствие ломает только
загрузку документов, то есть главы про проверку поставщика, и ломает молча (toast с ошибкой,
пустой список).

**Права `app_user` в свежей базе выдаются ДО миграций, и миграции их не выдают.** Семь таблиц
(`budgets`, `channel_connections`, `document_counters`, `followup_*`, `whatsapp_delivery_receipts`)
создаются без собственного `GRANT`, а живут они на умолчании, которое приёмка проставляет
своей рукой (`.github/workflows/acceptance.yml`) — в чужой базе его нет, и сид падает на
`permission denied for table budgets` посреди работы, оставив базу наполовину засеянной. То
есть лечится это не повтором сида, а пересозданием базы. Те же четыре строки, что у приёмки,
сразу после `CREATE DATABASE`:

```sql
GRANT CONNECT ON DATABASE <база> TO app_user;
GRANT USAGE ON SCHEMA public TO app_user;
ALTER DEFAULT PRIVILEGES FOR ROLE leadprocure_owner IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;
ALTER DEFAULT PRIVILEGES FOR ROLE leadprocure_owner IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO app_user;
```

```bash
GUIDES_PG_CONTAINER=leadprocure_postgres GUIDES_DB=leadprocure_guides \
FORCE=1 node scripts/produce-guides.mjs http://127.0.0.1:5179 az <ключи глав…>
```

Главы идут В ПОРЯДКЕ ИСТОРИИ и на одних данных, поэтому **пересъёмка одной главы в середине
не поддерживается — пересевайте стенд и снимайте всё подряд.** Здесь стоял совет «удалите то,
что глава создаёт (`DELETE FROM sourcing_events WHERE title=…`)», и он больше не работает:
удалить строки мало, на стенде остаются метки снятых глав (`guides_progress`), и прогон
откажет словами «Стенд ушёл вперёд истории». Готовый SQL делал этот совет убедительнее
верного, а привёл бы к отказу и к поискам поломки в стороже́.

Пересев обнулять метки не надо: они привязаны к поколению стенда — id организации, которую
заводит наполнение, — поэтому новое наполнение их просто не видит.

Запрет снимается `ALLOW_STALE_STAND=1`, но только для главы, числа которой от положения
стенда не зависят, и съёмщик при этом громко пишет, что запрет снят. Таких глав меньше, чем
кажется: даже «Параметры» показывают у отдела число заявок, а оно растёт от главы к главе.

Порядок курса (`apps/web/src/guides.ts`) теперь повторяет порядок истории: первый трек —
сквозная часть, в нём обе стороны идут вперемешку, потому что так это и произошло.

### Что осталось разрывом, а не недоделкой

`/buyer/invoices` закрыт для `BUYER_FINANCE` (`apps/web/src/main.tsx`, роли `BUYER`): человек,
которому по замыслу принадлежит сверка счетов, страницу не открывает, и в его меню её нет.
Главу про сверку снимает закупщик, и это сказано в самой главе. Это отдельная задача: роль
либо получает доступ, либо перестаёт называться финансистом.
